NextTransformer · 自动研究竞技场

Arena v2 设计图解

竞技场让 LLM agent 自己搜索语言模型架构，再在同一套训练协议下比 CORE-22 分数。v1 用规则和披露卡约束研究过程。v2 把研究过程放进一个 Gym：agent 在封闭容器里通过 22 个接口操作做实验，研究算力从固定额度里扣，最终训练交给可信的调度器。

Arena v1基于信任

agent 拿到仓库和任务说明，自己训练、自己选型、自己跑正式训练，最后用一张披露卡说明过程。

Arena v2由 Gym 执行

agent 只交模型源码和配置。训练、计费、打分、验证和最终训练，都由 agent 接触不到的服务完成。

架构：四个信任区

v2 的核心是把「谁能碰到什么」画清楚。Agent 能联网、能写代码，但拿不到 GPU、数据和检查点。候选代码只在沙箱里跑。验证和最终训练在 Agent 退出之后进行。

  • ① Agent 容器
    能联网、有 shell，但不持有任何训练资源。
  • ② 宿主机 Gym
    唯一的控制面，管实验、资源、数据、源码和预算。
  • ③ 沙箱 Worker
    候选代码唯一会被执行的地方。
  • ④ 交付之后
    验证与最终训练，Agent 退出后才开始。

研究流程：从接入到正式成绩

Agent 一侧的全部动作就是这 22 个操作。MCP 工具和 Python 的 GymClient 走同一个 HTTP 接口，共用凭据、错误码和预算账户。

  1. 接入

    容器里的 /run/gym-auth/credential.json 给出 endpoint、token 和 session_id。之后每次调用都是带 Bearer token 的 JSON 请求，发到 POST /v1/call。

  2. 了解搜索空间

    先读接口 schema、候选契约和 profile 的固定值，再看已发布的历史实验和批准的参考源码。

    • describe_space
    • get_resources
    • list_components read_reference
    • list_experiments read_experiment

  3. 提交候选

    上传一个只含源码的 ZIP。Gym 只查结构和字段类型，不导入代码。源码或配置一变，就是一个新的不可变候选。

    • submit_candidate 幂等键
    • list_candidates get_candidate

  4. 预检

    先看静态的 FLOPs 和参数量，再跑要计费的数值检查。校准一次可以比较 1–32 组完整配置，不训练。

    • inspect_cost
    • calibrate_candidate 幂等键
    • debug_candidate 幂等键 扣额度
    • validate_candidate 幂等键 扣额度

  5. 实验

    先报价，再按报价训练到一个绝对目标步数。可以从本服务返回的检查点续训。训练多久、跑几个候选，由 agent 自己定。

    • quote_experiment
    • run_experiment 幂等键 扣额度
    • get_job get_result read_events
    • cancel_job 幂等键
    • get_budget

  6. 冻结

    用最终 profile 做完整验证。admitted 为真、账户没有未结算的预留、没有活动任务，才能冻结一个候选，然后把回执写进 /workspace/submission.json。

    • validate_candidate（最终 profile）
    • finalize 幂等键
    • get_submission

  7. 交付之后

    Agent 退出时，Harbor hook 停止研究、结算任务并生成签名证据。独立验证器核对回执。可信调度器从全新初始化开始最终训练，审计并导出之后才有 CORE-22 成绩。这一步没有 agent 可调用的操作。

幂等键 需要 1–128 字符的 idempotency_key；输入不变时重试用原键 扣额度 从会话的研究 FLOPs 额度里扣

算力账本：一个额度，用完即停

v1 的研究算力不设上限，只要求披露。v2 给每个研究会话一个固定的 FLOPs 额度，训练、评估、数值检查和失败的尝试都从里面扣，不按候选分配。

1.96 × 10²⁰ FLOPs每个模型的一次研究会话。三个模型合计 5.88 × 10²⁰，最终正式训练另计。

一次数值操作怎么记账

  1. 报价quote_experiment 给出费用上界。报价绑定源码、profile、运行时、检查点、执行位置和目标步数，五分钟后过期，只能执行一次。此时不预留额度。
  2. 预留run_experiment 在同一个 SQLite 事务里预留报价上界并创建任务。GPU 忙时任务带着预留排队，不扣数值费用，也不回退到 CPU。
  3. 执行每次数值操作前先持久化操作意图并得到控制器确认。worker 用唯一的计费标识报告完成。
  4. 结算按实际工作量结算。验证指标由可信代码根据预测和标签计算，不接受候选自报的分数。

出问题时

情况账本处理
已知的数值失败扣本次操作的保守上界，报告 numerical_failure
取消在已结算的数值边界停下
worker 未知失败预留保留，任务进入 reconciliation。管理员确认 worker 已停后，扣掉剩余的保守预留；不退款，重复请求不重复扣
额度耗尽停止工作。最终训练的额度耗尽时报告 budget_stopped

不在这个额度里的

  • Agent 的模型调用。首轮实验不设费用上限，只记录 token 和实际费用；配置里的 agent.max_budget_usd 是可选项。
  • 网络搜索和容器内的 shell CPU，由 Harbor 或供应商另行限制。
  • 静态形状审计（inspect_cost、校准），不消耗数值研究 FLOPs。
  • 最终正式训练，使用独立的有限额度。

排期参考：路线图按 v1 搜索 549.7 加移植核对 42.1 共 591.8 GPU 小时，留 20% 余量，估每个模型约 710 GPU 小时，同类 8 卡环境约 89 小时。GPU 小时不是额外的硬上限。

数据边界：研究能看到哪些反馈

v1 靠规则要求 agent 不用保留数据选型。v2 里 agent 根本接触不到数据文件，能得到的反馈只有 Gym 返回的结果。

这条边界限制的是新候选能得到的反馈。已发布的历史 CORE 结果和公开网络信息 agent 仍然可以读到，设计文档明确说不保证 agent 从未接触公开基准。

候选包与隔离

Agent 的研究产物是一个原生插件加一份模型配置。研究用的 worker 和最终训练加载同一份源码，中间没有表达式语言或源码转换。

候选包（契约 reference_plugin_v1）

proposal.json        方法名、父候选、假设
architecture.json    原生 ModelConfig 字段和插件 options
plugin/<method>/method.json
plugin/<method>/__init__.py
plugin/<method>/…    可选的本地 Python 模块
  • ZIP 和解压后内容各不超过 1 MiB，最多 32 个 UTF-8 文本文件。
  • 每个会话最多保留 128 个候选，候选不可变。
  • 原生 hook 有 model、mixer、ffn、block；model hook 必须继承 ReferenceLM。
  • 宽度、头数、上下文长度、词表和 scale 由 profile 固定，显式填写时必须一致。
  • 拒收：权重、二进制、依赖安装器、训练脚本、符号链接、路径穿越，以及写在配置里的优化器设置、数据路径和命令覆盖。

Worker 隔离后端

后端隔离方式
bwrap
默认		全新的 bubblewrap 用户、挂载、PID 和网络命名空间。CUDA worker 只拿到选定的 NVIDIA 设备
landlockLandlock 路径规则，加用户、网络、IPC 和 UTS 命名空间。用于禁止挂载的宿主机，例如非特权 Kubernetes Pod。隔离弱于 bwrap：CUDA worker 保留宿主 PID 命名空间，能打开所有 NVIDIA 设备节点
none不隔离，只用于可信候选。启动时打印警告

后端由运维选择，Gym 不会自动切换。隔离的 worker 只能读运行时库、平台代码、批准的数据，以及当前任务的检查点和输出。

v1 → v2：改进了什么

  1. 约束从「规则加披露」变成「接口加账本」v1 的规则只能在提交时检查卡片和 PR 的改动范围。v2 的 Gym 在每次调用时检查 schema、权限和预算，不合规的请求直接被拒绝。
  2. 研究成本从披露变成控制v1 的规则自己写明，预算不受控，研究者之间的比较只是描述性的。v2 让每个模型用同一个 harness、同一份快照、同一个额度。
  3. 正式结果从自报变成可信流程产出v1 由参赛者在自己的 fork 上跑正式训练，默认 self-reported。v2 的冻结、验证和最终训练都不经过 agent。
维度Arena v1 · 基于信任Arena v2 · 由 Gym 执行
研究环境 把任务说明和一份仓库交给 agent。agent 在自己的机器上用 nexttransformer.train --smoke-steps N 或自写训练循环做实验。 Harbor 格式的任务。agent 在封闭容器里，没有仓库检出、GPU 和检查点，只能通过 Gym 的 22 个操作做实验。
研究算力 任意规模、任意数量，只要求披露。GPU 小时没计量时可以填 null。 每会话固定 1.96 × 10²⁰ FLOPs，自动计量。训练、评估、检查和失败的尝试一起扣，用完即停。
保留数据 规则禁止用验证分片和 CORE-22 选型，执行靠自觉和披露。 agent 接触不到数据文件。新候选的 CORE-22 分数要到冻结并完成最终训练后才产生。
候选形式 fork 里的插件目录，加校准配置、算力证明集、测试和模型卡。arena --scope 把 PR 的改动分成允许、需审查和禁止三类。 一个不超过 1 MiB 的源码 ZIP。上传时不导入代码，结构不合规直接拒收。插件契约与 v1 相同，所以研究和终训用同一份源码。
提交物 提案 issue 预注册，然后提一个 PR：插件、配置、算力证明、测试、模型卡、运行记录、审计、运行说明和披露卡。 finalize 冻结一个候选，交付一份三字段的回执。源码和配置留在 Gym 里，不从 agent 的工作区导出。
正式训练 参赛者自己在 fork 上用 8、16 或 32 张 GPU 跑 --formal，再自己审计和导出。 可信调度器在提交通过验证后，用独立额度从全新初始化开始训练。提交后 profile 有变化就拒绝启动。
核验 维护者默认不重跑。靠锁定的数据、固定的种子、公开的检查点和完整披露让结论可以被检验。 HMAC 签名的证据，加一个没有网络的独立验证器容器。验证指标由可信代码计算。
过程披露 手写披露卡：LLM、框架、人类参与等级 L0–L3、候选数、GPU 小时、选择信号。 算力账本由 Gym 记录，研究轨迹由 Harbor 收集，研究成本自动披露。
研究者比较 每个条目的算力、框架和人类参与程度都不同，只能并列展示。 等算力对比：Opus、GLM、DeepSeek 都用 Claude Code 加 Gym MCP，各 1.96 × 10²⁰ FLOPs。计划做按研究者排名的排行榜。
代码隔离 首个 v1 条目的研究在没有进程隔离的可信 agent 代码下进行，agent 的检出里有 results/，训练进程读得到验证分片。 候选代码只在 bwrap 或 landlock 沙箱里运行，读不到控制器状态和凭据，没有宿主网络。

没有变的部分

  • 参考训练协议 nextt-reference-50b-v1：49.152B 输入 token，46,875 次更新，每次 1,048,576 token，seed 42，训练成本在每 token 4.672 GFLOPs 的 ±1% 以内。
  • 排名方式：只用第 46,875 次更新时实测的 CORE 分数，这条规则在 11 月 6 日已经加进 v1。
  • 原生插件契约。一个新架构仍然是一个插件目录。
  • 正式运行从头开始，研究阶段的权重永远不带进去。
  • 允许查文献和上网。

设计文档自己列出的限制

  • 支持范围是一台本机，每份服务状态同时只跑一个数值任务，一次只运行一个研究 trial。远程调度和并行的独立数值任务不在范围内。
  • 原生 Python 与计费、评分代码在同一个进程里。命名空间隔离不能证明系统能抵御恶意 monkeypatch、伪造的 worker 消息或隐藏计算，当前路径假设候选代码遵守协议。
  • 静态审计追踪的是所选的原生执行路径，不覆盖所有依赖数据的分支。
  • 测试夹具的正式 BPB、CORE 和排名保持 null。开发测试不运行完整的 49.152B-token 协议。
