对象：detectron2，同一份输入，nanolize 的两个版本af5b2c7（PR #43）对 21d8a28（PR #45）2026-11-20依据：两组运行的记录 + 两个提交之间的代码差异

PR #45 在 detectron2 上有没有变慢

同一份 detectron2 输入、同样的设置（parallel 关，pair 开，Fable 5.2 high），在 nanolize 的两个版本上各跑一次，一组跑完再跑下一组。PR #43 版本用了 233.8 分钟，PR #45 版本用了 242.5 分钟，多 8.6 分钟（3.7%）。没有出现 tqdm 上那种接近一倍的差距，多出来的时间也不在 PR #45 改过的代码里。

结论 1

没有明显变慢

总用时 233.8 → 242.5 分钟，多 3.7%。两组结束的状态相同，都修了 2 次，交付的体积是原版的 23.1% 和 22.4%。tqdm 上同样两个版本是 107.5 → 202.9 分钟，1.89 倍。

结论 2

PR #45 改过的代码没有变慢

输入完全相同的基线 1：26.1 → 25.4 分钟。两次基线里敲除那一段都更短（14.6 → 13.6，20.4 → 17.8 分钟）。测试设计里的试跑多 6.6 分钟，是因为这一组的设计者多交了 10 份提案。

结论 3

看到一个隐患，这次的代价是 40 秒

PR #45 把录基线的批次上报的时间需求从 4 遍改成 6 遍。PR #45 版本录基线 2 时需求算成 159 分钟，节点只剩约 144 分钟，于是拒收、另开节点。排队忙的时候这一步会等得久；多报的两遍在 parallel 关着时并不执行。

每个版本只跑了一次。这里能排除的是“PR #45 会让流程成倍变慢”，排除不了几个百分点的差别。两组的运行时段和计算节点不同；tqdm 那三次做了性能验收，这次 detectron2 没有做。

  • 两组的形状相同。草稿作业一个 scope 接一个地写，五个会话合计 124.3 和 129.8 分钟；主作业的冻结是基线 1、测试设计、基线 2；封存之后都修了 2 次。

和 tqdm 的三次放在一起

tqdm 的三次是之前在 main 上的三次同配置运行（pair 开，parallel 关，做性能验收）；detectron2 的两次是这次的实验（不做性能验收）。同样是从 PR #43 版本换到 PR #45 版本，tqdm 是 1.89 倍，detectron2 是 1.04 倍。

  • 如果 tqdm 第 3 次慢是 PR #45 的代码造成的，同样的代码在 detectron2 上也应该慢。这里没有：改过的代码执行的三步合计只多 5.2 分钟，而且来自提案更多。
  • tqdm 第 3 次多出来的 95 分钟里，PR #45 改过的代码执行的步骤只占 11 分钟，其余 84 分钟在封存之后的修复循环和冻结里追加的设计轮次（见 tqdm 那一页）。
  • 两个项目的差别在修复的轮数。detectron2 两组都修 2 次，封存之后 109.7 和 105.9 分钟；tqdm 三次是 1、2、4 轮，封存之后 29.2、38.7、100.7 分钟。

判断：波动、PR #45 的隐患，还是流程不稳定

不是 PR #45 让流程变慢

detectron2 上两个版本只差 3.7%。PR #45 改过的代码执行的地方没有变慢，输入相同的那一步还快了 0.7 分钟；多出来的 8.6 分钟在作者写首版和第一次修复的会话上，那里两个版本的代码和提示词都相同。tqdm 第 3 次的翻倍不能归到 PR #45 的代码上。

PR #45 确实带了一个隐患，但它不是 tqdm 变慢的原因

录基线的批次按 6 遍上报时间，这次让节点拒收了一个按 4 遍算放得下的请求。这次只花了 40 秒；集群排队的时候可能是几分钟到几小时，而 parallel 关着时多报的两遍并不执行。tqdm 的第 2 次和第 3 次里，基线 2 本来就都是另开节点跑的，这个改动在那里没有造成差别。建议修掉：只在检查并发打开时才多报。

是流程对模型每次写出的内容敏感，tqdm 把它放大了

同一份输入跑两次，模型写出的东西不一样。这次 detectron2 的两组：提案 49 对 59 份，封存的检查 92 对 96 个，场景用例 270 对 412 个，写首版 124.3 对 129.8 分钟，第一次修复 29.6 对 35.9 分钟，controller 的走法也不同。这些差别在 detectron2 上互相抵掉了（冻结慢的那一组不用等草稿），修复都是 2 次，所以总用时接近。tqdm 上修复的轮数是 1、2、4，每多一轮就是二三十分钟的修复加一次全量的性能重测，差距就被拉开了。所以 tqdm 的问题属于流程本身不稳定带来的运行间波动，不是哪一个版本的代码。

只凭这两次还说不了的

每个版本只跑了一次：同一个版本在 detectron2 上重复跑会差多少，这里没有测，3.7% 可能就在这个范围里。tqdm 的放大来自它自己的特点（帮助文字由文档字符串生成，做性能验收）；这次 detectron2 没有做性能验收，性能那条路径没有被检验。

口径

  • 两组的输入相同：detectron2 的同一个提交、同一份功能图和检查清单。nanolize 分别是 PR #43 的合并提交 af5b2c7 和 PR #45 的合并提交 21d8a28。main 后来回退了 PR #45，所以两组各用一份固定在自己提交上的代码副本，不用 main 现在的状态。
  • 设置两组相同，逐项核对过：pair 开；两个作业的配置里都没有 parallel 这一项；检查的 workers、cpus 都没有设；模型 Fable 5.2，effort high（每一次模型调用的记录里都是）；不做性能验收。两组启动参数的差别只有解释器所在的提交。
  • 两组一前一后跑：第一组结束并归档之后才提交第二组，中间没有别的 nanolize 作业在跑。两组申请的资源相同，落在不同的计算节点上。
  • 时间从主作业的第一条事件算到最后一条事件。各步的时长取自作业的操作记录，模型会话取自每次调用的记录。
  • “每个检查跑 3 遍”的时长是基线记录里每一遍时长之和，两组算法相同。PR #45 版本另有每 10 秒一次的采样，记下了节点接每个请求的时刻（基线 1：跑检查 12.0 分钟，敲除 12.2 分钟；基线 2：21.8 和 16.3 分钟），和上面的算法对得上。PR #43 版本的采样是中途才加的，冻结那一段没有。
  • 时间需求是按 nanolize 里的公式重算的：需求 = 2 × 遍数 × 跑一遍预计 + 10 分钟，上限 240 分钟；跑一遍预计用基线 1 量到的时长和作业自己记下的检查用时；节点剩余的时间按 240 分钟减去已经用掉的、再减 1 分钟。请求文件作业用完就删，所以这是重算，不是读出来的，可能差一两分钟；它和实际发生的一致（一组留在原节点，一组被拒收）。
  • tqdm 的数字来自之前三次运行的轨迹，分析在另一页。tqdm 做性能验收，这次没有做，两个项目的总用时不能直接比，只比同一个项目里两个版本的比例。
  • 页面里去掉了：账号名、队列和分区名、机器名、本地路径、调度器的作业编号。
