① 每一轮：谁决定下一步 两种模式相同

作业是一个循环。每一步之前，主线先算出「默认下一步」，再问 controller。它的回答有四种，决定这一轮怎么走。循环到交付或停止为止。

R1

一批调用

controller 回答calls 调用 1 调用 2 … 最多 24 个 再问 controller

按顺序一个一个执行，每个调用在日志里记一行。

R2

只委托给主线（follow）

controller 回答follow：走到哪个阶段、最多几步 主线一步 主线一步 … 默认 10 步，最多 20 再问 controller

委托的步骤算在这一轮里，不消耗轮次。一个只写 follow 的回答可以把整条主线跑到需要决策的地方。

R3

调用 + 委托

controller 回答calls + follow 调用 1 … N 主线一步 … 再问 controller

先跑自己选的调用，主线从它们停下的地方接着走。批次中途被截断（B5）就不委托。

R4

没有可用的回答

回答在任何调用执行前就被拒同一轮内改正一次
回答无效，或 agent 不可用执行默认的一步下一轮再问
连续 3 轮没推进，或轮次、时间、token 用完之后每一步都走默认

默认的一步就是主线（见 ③），所以作业总能往前走，这时等同固定流水线。因连续没推进而停问的，恢复作业后会重新问。

委托在什么时候停下、回来问 controller

  • 主线走到了停止，或作业已交付。
  • 下一步所属的阶段超过了 follow 指定的阶段（顺序：freeze → tasks → rewrite → verify → effort → deliver）。
  • 轮到要做决定：修复、优化、恢复某个候选、失败、暂停；没指定走到 deliver 时还包括交付。
  • 走满了步数。
  • 上一步被拒、输出被拒，或结果不是主线能接着走的（例如比较发现了失败）。
  • 这期间 owner 动过作业：授权修订、调用了非查询工具、暂停或恢复。

作业最后怎么结束 两种模式相同

交付

  • succeeded：没有缺口。
  • completed_with_gaps：没有失败，但有补不上的缺口。
  • delivered_with_failures：带着列明的失败交付。

暂停，可以恢复

  • 模型服务拒绝或中断会话（限流、认证失败）。
  • 输出连续 3 次被拒（没设尝试上限时）。
  • 时间或 token 用完，且没有通过验收的候选。
  • owner 在场，controller 带 wait 提了问。
  • owner 手动暂停（hold）。
  • 基线不可用或冻结输入变了，而 controller 这一轮没给出可用的回答。

  • 作者尝试用完，且没有任何可以交付的东西。

依据：strategies/controller.py（轮次、批次、委托）、strategies/advice.py（主线和并行主线）、job_tools/workspaces.py（工作区批次和并行组）、controller 的指南提示词，以及 tests/test_parallel_mainline.py 里的用例。网址后面加 #off 或 #on 可以直接打开对应的视图。
