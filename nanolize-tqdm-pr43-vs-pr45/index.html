对象：tqdm，同一份输入，nanolize 的两个版本af5b2c7（PR #43）对 21d8a28（PR #45）2026-11-21依据：两组运行的记录 + 两个提交之间的代码差异

PR #45 在 tqdm 上有没有变慢

同一份 tqdm 输入、同样的设置（parallel 关，pair 开，Fable 5.2 high，全部能力，不做性能验收），在 nanolize 的两个版本上各跑一次，一组跑完再跑下一组。PR #43 版本用了 71.0 分钟，PR #45 版本用了 81.9 分钟，多 10.8 分钟（15%）。两组走的步骤完全相同，没有出现之前 main 上 107.5 对 202.9 分钟那种接近一倍的差距；多出来的时间一多半在一次修复的会话上，不在 PR #45 改过的代码里。

结论 1

没有成倍变慢，慢了 15%

总用时 71.0 → 81.9 分钟。两组结束的状态相同，都是 controller 1 轮、修复 1 次、完整对比 2 次，交付的体积是原版的 55.2% 和 55.8%。之前在 main 上同样两个版本是 107.5 → 202.9 分钟，1.89 倍。

结论 2

PR #45 改过的代码没有变慢

输入完全相同的基线 1：2.6 → 2.2 分钟。三处敲除合计 10.0 → 7.5 分钟，而 PR #45 版本的检查还多 6 个。改过的代码执行的三步合计 31.2 → 32.0 分钟，多出的 0.8 分钟在试跑上：设计者多交了 7 份提案。

结论 3

多出来的时间主要是一次修复

两组的第一版坏在不同的地方。PR #43 版本坏的是进度条的一处收尾，2.0 分钟修好；PR #45 版本的作者改写了 --help 里的选项说明，而这些说明要和原版逐字相同，修了 8.0 分钟。这一项占了多出的 10.8 分钟里的 6.0 分钟。

每个版本只跑了一次。这里能排除的是“PR #45 会让 tqdm 成倍变慢”；15% 的差别是不是每次都有，一次对照说不了。这次不做性能验收，之前 main 上那三次做了。

和之前的几次放在一起

三组实验：之前在 main 上的三次 tqdm（pair 开，parallel 关，做性能验收）；detectron2 上的对照（不做性能验收）；这次 tqdm 上的对照（不做性能验收）。同样是从 PR #43 版本换到 PR #45 版本，三处的比例是 1.89、1.04 和 1.15。

  • 如果 main 上第 3 次慢一倍是 PR #45 的代码造成的，这次同样的代码、同一个项目也应该慢一倍。这里是 1.15 倍，而且两组的步骤完全相同。
  • 这次的两组比 main 上的三次都短，不能直接比：这次不做性能验收，功能图和检查清单也是另一次准备的（32 项能力、22 个原有检查）。只比同一组里两个版本的比例。
  • main 上三次的修复（行为加性能）是 1、2、4 轮，封存之后 29.2、38.7、100.7 分钟；第 3 次多出来的 95 分钟里，84 分钟在封存之后的修复循环和冻结里追加的设计轮次（见 那一页）。这次两组都只修 1 轮，封存之后 10.2 和 18.2 分钟。
  • detectron2 上的对照见 这一页：233.8 对 242.5 分钟，两组都修 2 次。

判断

PR #45 的代码没有让 tqdm 变慢

两个版本在 tqdm 上差 15%，步骤完全相同。PR #45 改过的代码执行的三步合计只多 0.8 分钟，其中敲除更短（10.0 → 7.5 分钟），多出来的是检查和提案更多。上报时间的那个改动在 tqdm 上没有触发。main 上第 3 次的翻倍不能归到 PR #45 的代码上，这和 detectron2 上的结论一致。

多出来的 10.8 分钟来自两组模型写出的内容不同

第一版坏在哪里不同，修复 2.0 对 8.0 分钟（+6.0）；设计者交的提案 56 对 63 份，返修的设计者 1 个对 3 个，会话 +2.4 分钟；封存的检查 74 对 80 个，完整对比和试跑一共多 2.4 分钟。这些地方两个版本的代码和提示词都相同。

tqdm 的那个放大点这次又出现了，只是没有被放大

PR #45 版本那一组的第一版改写了 --help 的选项说明。这正是之前分析里 tqdm 自己带来的不稳定：命令行的帮助文字由文档字符串生成，要和原版逐字相同，而作者写第一版时不照抄原版的文档字符串。main 上第 2 次、第 3 次的第一轮行为修复也是这一类问题（5.8 和 13.9 分钟）。这次它花了一次 8.0 分钟的修复，修完就过了；main 上第 3 次是修帮助文字时又弄坏了一条原有的测试，再加上两轮性能修复，一共修了四轮。它落在哪一组是碰巧的：PR #43 版本那一组的第一版体积相同（55.2% 对 55.1%），没有踩到。

只凭这两次还说不了的

每个版本只跑了一次：同一个版本在 tqdm 上重复跑会差多少，这里没有测，15% 可能就在这个范围里（main 上第 1 次和第 2 次是相邻的两个版本，差 7%）。这次不做性能验收，main 上拉开差距的“修复之后重测性能”那条路径没有被检验。要把“运行间波动”量出来，需要同一个版本、同一份输入重复跑几次。

口径

  • 两组的输入相同：tqdm 的同一个提交、同一份功能图和检查清单（32 项能力，22 个原有检查），都从同一份保存好的准备结果恢复。nanolize 分别是 PR #43 的合并提交 af5b2c7 和 PR #45 的合并提交 21d8a28。main 后来回退了 PR #45，所以两组各用一份固定在自己提交上的代码副本，不用 main 现在的状态。
  • 设置两组相同，逐项核对过：pair 开；两个作业的配置里都没有 parallel 这一项；检查的 workers、cpus 都没有设；模型 Fable 5.2，effort high（每一次模型调用的记录里都是）；全部能力；不做性能验收。两组启动参数的差别只有解释器所在的提交。
  • 和 detectron2 那次对照的设置有两处不同。一是范围：这次选全部能力，那次选的是核心能力。二是那次把 nanolize 所有版本的代码副本都对模型会话遮住了，连带让作者提示词里点名的 token 计数命令跑不起来；这次每一组自己版本的那一份保持可见，其余版本仍然遮住，作者能看到自己代码的 token 数。开跑前用不调模型的自检确认过：计数命令能跑，会话里的解释器都导入不了原版 tqdm。
  • 两组一前一后跑：第一组结束并归档之后才提交第二组，中间没有别的 nanolize 作业在跑。两组申请的资源相同，落在不同的计算节点上。
  • 第二组跑了两次才成。第一次开始 1 分钟后，主作业向调度器查询节点状态时超时，自己暂停了，当时还没有创建任何东西。原地恢复会让草稿作业比主作业多跑几分钟，和第一组不对等，所以取消了这一次，现场另存，再原样重新提交。本页用的是重新提交的那一次；作废的那一次只有试运行器的 0.15 美元和草稿作者约 3 分钟的会话。
  • 时间从主作业的第一条事件算到最后一条事件，在调度器里排队的时间不算。各步的时长取自作业的操作记录，模型会话取自每次调用的记录。
  • “每个检查跑 3 遍”的时长是基线记录里每一遍时长之和，两组算法相同。两组都从一开始就每 10 秒采样一次检查节点的记录，记下了节点接每个请求的时刻；敲除本身的时长取自这份采样，精度约 10 秒。
  • 时间需求是按 nanolize 里的公式重算的：需求 = 2 × 遍数 × 跑一遍预计 + 10 分钟，上限 240 分钟；节点剩余的时间按 240 分钟减去已经用掉的、再减 1 分钟。请求文件作业用完就删，所以这是重算，不是读出来的，可能差一两分钟。
  • 草稿作业自己的基线在两组里都被判成“不能当验收依据”（有 6 项能力没有原有的检查），草稿照常写，验收由主作业封存的合同来做。两组相同。
  • 两组结束的状态都是“带缺口交付”：5 个原检查里有测试函数没能进入验收（PR #43 版本 4 个，PR #45 版本 2 个）。交付之后在交付的代码上回放了没进验收的 93 个原测试，两组都没有退步。
