tqdm 第 3 次比第 2 次慢在哪

同一个 tqdm 实验在 main 上跑了三次。第 2 次用 main af5b2c7（PR #43 合并之后），107.5 分钟；第 3 次用 main 21d8a28（又合并了 PR #44 和 PR #45，并行修改就在 PR #45 里），202.9 分钟。这一页把两次运行画在同一把时间尺上，回答两件事：多出的 95.4 分钟花在哪里；并行计划和并行进度两页里的设计，在第 3 次里处在什么状态。

结论 1

并行设计没有失效：这次运行里它没有打开

提交的选项是 pair=on（两个作业），没有打开 parallel 模式，也没有设 workers。PR #45 带来的 10 个并行子项，这次只走到 1 个，而且看不出效果。

结论 2

变慢不是 PR #44、PR #45 带来的

两个提交之间，测试设计这一步的代码没有变，提示词只改了并行模式才用到的那一段。模型输出的速度、节点跑检查的速度，两次相同。更新过的代码执行在哪几步，图里用红框标出。

结论 3

多出的时间是一步接一步的模型工作

这次设计者写的测试更多，作者的第一版删得更狠，封存之后修了 4 次（第 2 次 2 次）。修复是一次接一次做的，并行计划里没有管这一段的改动。

三次各只跑了一遍。第 1 次（main 3381471）实际 115.0 分钟，它和第 2 次之间隔着 PR #43 的 111 个提交，用时只差几分钟；第 2 次和第 3 次之间只隔 7 个提交，却差了一倍。差别来自模型每次写出的内容，单次运行的用时不能用来判断一项代码改动的效果。

两次运行，同一把时间尺

横轴是主作业开始后的分钟数，按比例画。每次运行五行：草稿作业；设计者和评审的会话（一条线是一个会话，上下叠着的同时在跑）；作者修复和 controller 的决定；在计算节点上跑的检查和固定步骤；等节点。

  • 冻结多 33.4 分钟，封存之后多 62.0 分钟。第 3 次封存之后的时间是第 2 次的 2.6 倍。
  • 草稿作业两次都早早写完，然后空等。第 2 次空等 25.1 分钟，第 3 次 65.5 分钟。它不在关键路径上，写得再快，作业也不会早结束。
  • 设计者和评审的会话本来就是同时跑的。一轮最多 28 个，墙钟由最慢的那个会话决定。
  • 封存之后是一条线。controller 决定、作者修复、保存、行为对比、安装检查、性能对比，一步接一步；有一条没过，就从头再走一圈。

口径

  • 两次运行的设置相同：同一个 tqdm 提交、同一份功能图（35 项能力、32 条检查）、同一份提示词、pair=on、performance=on、effort=high、无人值守、检查在计算节点上跑。不同的只有 nanolize 的代码版本。主持会话开放给模型会话的目录第 2 次多两个（Python 解释器的目录）；第 1 次和第 3 次一样是两个，用时和第 2 次接近，所以不把它算作原因。
  • 时间取自两次运行各自的轨迹（作业的事件和操作、每个模型会话、调度器的记账），用的是实际时钟。同一实验的报告页扣掉了等节点的时间，所以那里是 103.0 和 193.7 分钟，这里是 107.5 和 202.9 分钟。
