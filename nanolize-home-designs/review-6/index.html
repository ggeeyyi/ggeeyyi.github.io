版本 6 设计评审

版本 6 停下来的那一幅画（?t=18）已经是成品：细线画成的绿色子图、一行衬线标题、真实的仓库和模块名。八位评审没有一位要改子图本身的画法。问题不在画得不好，而在三处。第一，文字和画面讲的不是同一个故事：文字说“从零重写成一个一半大小、行为不变的新仓库”，画面演的是“把代码画成图，点亮值得留下的那一半”，而且从头到尾没有出现过 nano 仓库本身。第二，每一轮的结尾把结果倒着撤销了：读数从 382 / 382 退回 0 / 382，绿色的子图化回乱图，再变回原来的代码。第三，首屏说得太多、停得太少：同一组数字在三百多像素里叠了三层（其中一层是跑马灯），开场那一屏最挤，成品在 24 秒里只静止 4.9 秒。这些几乎都能靠删、合并、改字解决，只有“让 nano 仓库露面”是新的一轮设计。

怎么读这份报告：

  • 八位评审各用一个角度看页面。看“贴不贴主题”的三位：T1 第一次来的访客，T2 画面有没有如实讲方法，T3 把整页从头读到尾的研究者。看“简洁和高级感”的五位：P1 美术指导，P2 专做减法，P3 动效，P4 细节做工，P5 拿最好的同类页面来比。
  • 改动大小：小是一两个小时，中是半天到一天，大是新的一轮设计。
  • “在哪里看”里的 ?t=18 是加在网址后面的参数，页面会停在那一秒。
  • 几个词：“读数”指动画下面那两行横条和数字；“阶段文字”指读数上方那行小字（比如 “detectron2 · delivered”）；“跑马灯”指三个大数字下面那条横着滚动的结果条；“停留”指 16.5 到 21.4 秒成品静止的那一段；“图 2”指你给的第二张图（文件树、图、选中的范围、nano 仓库四格）。
  • 所有判断都来自定格的截图和连拍，没有人看过页面真正跑起来的样子。凡是关于快慢和手感的改动，改完要再看一遍。评审有分歧、或者决定先后次序的地方，我自己重新截图核对过：21.8 秒的读数、开场一屏、生长和检查的连拍、首屏底部、1280×720 的窗口、手机、防火墙一节。

一、更贴合 Nanolize 的主题

1. nano 仓库从头到尾没有露面

  • 问题：一轮从一个仓库开始（文件树加代码），却没有以一个仓库结束。图 2 有四格，版本 6 做了前三格；第四格是一棵短的绿色文件树，下面是代码量和检查数，也就是产品交出来的东西，页面上没有。访客看到的是“仓库进去，一张发光的图出来”，那是代码可视化工具的故事。往下翻完整页，也没有一处给人看一眼 nano 仓库长什么样、少掉的是哪类代码。
  • 在哪里看：?t=18。停留的五秒里画面没有再讲新东西。对照图 2 最右一格。
  • 怎么改，分两步：
    • 第一步（中）：在首屏下面、方法和结果两节之间加一块“出来的是什么”。挑一个库（tqdm 或 requests），原仓库和 nano 仓库的文件树并排，用首屏文件树的画法，每个文件夹标上 token 数，再用一句话说少掉的是哪类代码。手机上也放得下。
    • 第二步（大）：停留时让一棵绿色的短文件树在子图右侧一行行出现，根那一行是 仓库名-nano/，虚线从子图上带名字的星连到它的各行，正好是 3.5 到 4.2 秒那一幕反过来。访客看到的是开场那棵树，短了一半，变绿了。宽 1440 的窗口里子图右边正好空着约 190 像素；手机上不放，只留第一步。
    • 两步都要 nano 仓库真实的文件列表，工作区里现在没有。页面的规矩是每个名字都核对过，所以不能照图 2 写 core1.py。另外图 2 上的数字（−49.43%、722 / 722）和页面上的（−49.44%、549 / 549）不一样，以页面为准。
  • 改动：第一步中，第二步大。
  • 评审：T1、T2、T3、P5。四位各自独立提出，T1 和 T2 都把它排在第一。

2. 中段的画面是“挑出一半留下”，字却写着“从零重写”

  • 问题：7.2 到 11.8 秒，绿色沿着乱图里原本就有的线走，把原本就在的白星一颗颗点绿，旁边的星变暗。这个画面的意思是“从旧代码里挑出一半留下”，也就是裁剪。同一时刻阶段文字写的是 “rewriting from scratch”（从零重写）。裁剪正是最容易和 Nanolize 混淆的那类工具，而页面下面的结果表恰恰在说它和这类做法不一样。现在唯一演出“从零”的，是屏幕底部那条 3 像素高、从 0 涨起来的绿条。
  • 在哪里看：?t=8、?t=9。我的连拍里，7.7 到 9.2 秒绿色是在还亮着的白色乱线上走的。
  • 怎么改，分两步：
    • 先做（小）：这一段的阶段文字不再写 “rewriting from scratch”，改成画面真在演的事，比如 “nanolizing”。“从零重写”这句话由标题下面的说明、从 0 涨起来的数字和第 1 条里新加的 nano 文件树来讲。
    • 再试一版（中）：留下的星、线、形状、比例都不变，只调换先后。7.2 到 8 秒整片乱线先一起退掉，其余的星先暗下去；然后绿色从根出发，在安静下来的星空里一段段画出来，每颗绿星在线头到达时才出现。这样绿色看上去是新写的，不是从旧图里找出来的。这一段现在是两位评审眼里全轮最好的一段，所以做成单独一版，和现在的并排看了再定（见第三节第 1 条）。
  • 改动：小，加一版中等的试验。
  • 评审：T1、T2（都评为最要紧的两条之一）；T3 从整页的角度指出同一个矛盾。

3. 每一轮的结尾把结果撤销了

  • 问题：21.4 秒起故事倒着放。阶段文字从 “delivered”（已交付）跳回 “the same code, as a graph”；检查数从 382 / 382 一步掉到 0 / 382；NANO 的行数一路倒数到 0；绿色的子图褪回白色乱图，再变回那片臃肿的代码。每一轮最后的 2.6 秒，页面演的是它主张的反面。README 的约定 5 说 nano 的数字只从 0 往上涨、不往下减，这里正在往下减。
  • 在哪里看：?t=21.8。我核对过：子图还全亮着，读数已经是 “23,625 lines、0 / 382 pass”。再看 ?t=22.2、?t=23.2。
  • 怎么改：不倒放。21.4 秒起子图、名字和星空在一秒左右一起淡到暗，读数停在交付时的数字上跟着暗下去，暗了之后再换成下一个仓库；然后下一个仓库的代码淡入，它的文件树一行行展开（这个展开的动画现在就有）。如果舍不得“星星变回代码”那一下，至少做到三件事：读数不倒数，阶段文字不往回跳，旧的文件树不再回来一次。
  • 改动：小。
  • 评审：T1、T2、P2、P3、P5，五位。P3 另外指出这一段同时有六到八种东西在动，是全轮最乱的一段。这一条对“高级感”同样有用。

4. “行为全部保留”没有说实

  • 问题：标题说行为全部保留，画面里却有一多半的星暗下去。方法一节写“每个选中的功能”，用法一节写“从 Core features 或 All features 开始，再逐个开关”；只有 Detectron2 明说了 106 项能力全部保留。结果表里的八个库是不是也保留了全部功能，页面没说。研究者的第一个问题就是“少一半 token，是不是因为少了一半功能”，现在的画面加上用法那句话，正好让人往这边想。另外，“一项检查”是什么、token 数的是哪些文件，页面没有定义；more-itertools 少了 62% 却只有 10 项检查，不解释就显得单薄。
  • 在哪里看：结果一节的导语和表格下面那行小字；首屏三个大数字中间那一个的说明。
  • 怎么改：在结果一节的导语里加一句实话（如果属实：“每个库的每一项功能都保留”）；三个大数字中间那个的说明改成“行为检查通过，功能全部保留”；表格下面加一行，说清一项行为检查是什么、549 项背后有多少个测试用例、token 只数哪些文件。如果八个库其实只做了核心功能，标题就要加限定，这一点发布前必须确认。
  • 改动：小（只改字），但要从技术报告里拿到事实。
  • 评审：T3；T2 也把它列为“我判断不了、但会影响结论”的事。

5. 读数说的不是标题的话，也不是结果表的记法

  • 问题：读数是首屏唯一证明标题的地方，有四处对不上。
    • 标题说 “behavior”，读数说 “382 checks frozen”“running the frozen checks”。“frozen”（冻结）要到三节之后才解释，陌生人会读成“卡住的检查”。
    • 重写开始之前，NANO 一行有七到十二秒写着 “0 lines、0 / 382 pass”，看上去像一次失败的运行。
    • 八个库的那几轮，ORIGINAL 一行写 “100% tokens”，等于什么都没说。
    • 读数写“剩下多少”（tqdm 55.20% tokens），往下一点的跑马灯和结果表写“减了多少”（tqdm −44.80%）；Detectron2 那一轮又是行数，而标题讲的是 token。访客要自己做减法才知道说的是同一件事。
  • 在哪里看：?t=1（0 / 382 pass）；?t=18&repo=tqdm（100%、55.20%），再往下滚一点看跑马灯。
  • 怎么改：ORIGINAL 一行写 “382 behavior checks”，阶段文字写 “running the behavior checks”，“frozen” 留给方法一节；NANO 一行在轮到它之前显示一条短横，不显示 0；交付时阶段文字带上结果表的写法，“tqdm · delivered · −44.80% tokens”（Detectron2 是 “−52.6% lines”）；“100% tokens” 去掉，只留满格的横条。技术报告里如果有 Detectron2 的 token 数，它那一轮也改用 token。
  • 改动：小。
  • 评审：T1、T3、P2、P4、P5。

6. 第一次打开的前十几秒看不到主题

  • 问题：标题的两句话，画面要到 14 秒才第一次兑现。7.2 秒之前画面讲的是“代码可以画成图”，不是产品。只看十秒就走的访客，看到的是一面灰字的代码墙、一段最乱的飞散，读数上还写着 0 / 382。而且第一轮讲哪个仓库是随机的：九次里有一次是 tomli，文件树只有十行、18 项检查，配不上“臃肿的仓库”；每位访客看到的第一幅画都不一样，页面没有一张大家共有的“脸”。
  • 在哪里看：不加参数直接打开页面，看前十秒；?t=1&repo=tomli。
  • 怎么改：只在第一轮，页面一打开先停在成品上（detectron2 的神经元，就是减少动态效果时显示的那一幅，用 0.8 秒淡入），停五秒让人读完标题，然后回到代码从头讲。从头讲的第一个完整故事固定为 requests：名气最大，剩 49.51% 的 token，几乎就是标题那句话，检查 91 / 91。之后照旧随机。循环本身不用改。
  • 改动：小。
  • 评审：P3、P5（先亮成品），T1（固定第一个仓库）。

7. 开场的代码是编的，下面却写着真仓库的名字

  • 问题：文件树、子图上的名字、所有数字都是真的、核对过的，唯独开场那片代码是编的（class PipelineRunner、cfg.RUN.STAGES），每一轮都是同一片，下面却写着 “tqdm · the original code”“requests · the original code”。懂这些库的人一眼看出这不是 tqdm。它还故意写得很臃肿，多疑的读者会当成摆拍。这是一页报告实测数字的页面上唯一的假展品，偏偏在第一秒。
  • 在哪里看：?t=1&repo=tqdm 和 ?t=1&repo=requests 对比，树换了，代码没换。
  • 怎么改：每个仓库放它自己的一段真代码，取自文件树里有的一个文件，并把树里那一行点亮（tqdm 的 std.py、requests 的 sessions.py、detectron2 的 modeling/backbone/fpn.py）。八个库的源码已经取到，Detectron2 的要另取；引用前核对各自的许可证。做不了的话，最小的改法是把这行字改成 “the original repository”，对文件树来说这是真话。
  • 改动：中；最小版小。
  • 评审：T1、T2。用示例代码是 README 里早先写明的选择；文件树换成真的之后，它成了短板。

8. 文件树接到图上的那一刻只有 0.7 秒

  • 问题：文件树、虚线和星空同时在场，是全轮最贴题的一帧，也就是图 2 的左半。它只有 3.5 到 4.2 秒这 0.7 秒，而且这时星星还在飞、拖着尾线，虚线上的点也在移动，没有一样东西是静的，读不出来。紧接着 5.0 到 7.2 秒，乱图独自转了 2.2 秒，什么也没发生。
  • 在哪里看：?t=3.9，对比 ?t=6。
  • 怎么改：把静止挪到有意义的地方，一轮总长不变。星星在 4.2 秒前落定，虚线在星星落定时正好连上；树、虚线和落定的乱图一起静止到 5.8 秒左右再松开；时间从后面那段空转里出。
  • 改动：小，调几个时间。
  • 评审：T2、P3。

9. Detectron2 在下文没有着落，下文还缺几件事实

  • 问题：Detectron2 是定格画面用的仓库，也是最大、最有说服力的例子（7.7 万行的真实框架）。可它的 76,888 行、36,458 行和 382 项检查，在首屏以下哪里都找不到，结果表里也没有它这一行。宽屏上 “76,888 lines、382” 就压在 “−49.44% tokens、549” 上方一百像素，单位和数字都对不上。读到页脚还不知道的事：重写一次花多少 token 或多少钱（一个讲 token 的页面只给了时长）；是不是只支持 Python；Goal mode 是什么；方法一节的“五个阶段”是哪五个，合同由谁、从哪里提取。
  • 在哪里看：宽 1920 的窗口 ?t=18；“The next agent pays less” 一节；方法一节的第三条。
  • 怎么改：把 “The next agent pays less” 一节做成 Detectron2 的专场，开头用首屏那种两条横条写明 “76,888 行到 36,458 行，382 / 382，106 项功能全部保留”；方法一节第三条（五个阶段、三十九个工具，两个没有内容的数字）换成五个阶段的名字；用法一节下面加三四行事实；结果的导语用半句话解释 Goal mode，并把“只用三分之一的时间”说出来（1 小时 11 分对 3 小时 53 分）。
  • 改动：小到中，都要技术报告里的事实。
  • 评审：T3。

10. 几处小的

  • 子图上名字挂在哪颗星上是随便定的：layers 挂在 model_zoo 外面的枝梢上，懂 Detectron2 的人知道 layers 是底层。按真实的层级给名字，被依赖的靠近根。小。T2。
  • click 和 requests 点亮的名字里有 compat（兼容层）。在讲去掉臃肿的页面上，兼容层亮在 nano 的树上，意思是反的。换一个真实的模块名。小。T3。
  • 可选：检查的光经过一个模块时，名字从白变绿，后面出现一个小勾。“行为全部保留”在画面里就有了十三个看得见的证据。小。T2。
  • 标题下面那句话没解释 “nano”，也没说是谁在重写（访客自己的编程智能体）。小。T1。

二、更简洁、更有高级感

1. 首屏底部同一组数字叠了三层，其中一层是跑马灯

  • 问题：读数（这一轮仓库的两行）、三个大数字（八个库的平均）、跑马灯（八个库逐个滚动）一层压一层，再往下三屏是同样八行的结果表。−49.44% 出现三次，每个库的百分比出现三次，记法还有两种。跑马灯是整页唯一通栏的元素、唯一混用两种字体的一行，也是紧贴着会动的星空的第二个会动的东西。同样的话说几遍，再加一条跑马灯，正是让页面像产品落地页的两样东西。
  • 在哪里看：把窗口拉高到 1300 以上，?t=18&repo=tqdm，读数、三个数字、跑马灯都在一屏里。
  • 怎么改：删掉跑马灯。它有的，首屏的循环和结果表都有。首屏于是结束在三个大数字和它们的细线上。
  • 改动：小。
  • 评审：P1、P2、P5、T3，四位一致，没有人为它辩护。读数要不要并成一行、三个数字要不要搬走，评审有分歧，见第三节。

2. 成品停得太短，一轮里六成时间画面在变

  • 问题：成品是页面最得意、也最安静的一幅，在 24 秒里只静止 4.9 秒（两成）。访客抬头五次，有三次看到的是“正在变”。版本 6 新加的纵深只有靠转动才看得出来，而停留里只转了 28 度。最好的页面是演完、落定、停住。
  • 在哪里看：直接打开页面看一整轮。成品静止的只有 ?t=16.5 到 ?t=21.4 这一段；其余的时间里，代码、乱图各静止过 2.2 秒，别的时候都在变。
  • 怎么改：一轮从 24 秒加到 30 秒，多出的 6 秒全给停留（约 11 秒，转 62 度），别的时刻都不动。结尾改成淡出（第一节第 3 条）还能再省出一秒。另一个由你定的选项：五种形状各放一遍之后停在成品上，只留慢转；访客滚走再回来，或者点一下画面，再重新讲。代价是每次只看得到五个形状和仓库。
  • 改动：小。
  • 评审：P3、P5。

3. 开场那一屏是全轮最挤的一帧

  • 问题：每位访客看到的第一帧像一张编辑器截图。
    • 代码第一行离按钮只有 6 到 8 像素。
    • 长的代码行在栏边被硬切在单词中间（“str”“sel”“rename”），注释只剩 “# ke”，像没处理的溢出。
    • 文件树每一行后面的虚线在半空中断掉，像一份没有页码的目录，要到 3.4 秒才有去处。
    • 文件树（白、加粗、实心的文件夹）比代码还亮，眼睛先落在文件树上，不是标题上。
    • 手机上树只到七成高，左下角空一块；树的字 9.5 像素、代码 8.5 像素，两块都小得读不了。

三、评审之间的分歧

1. 中段“绿色长出来”的那一段，改不改

  • T1、T2：这段画面演的是裁剪，要改成“乱图先退场，绿色再新画出来”，否则访客会把 Nanolize 当成裁剪工具。
  • P2、P3：这是全轮最好的一段。一个前沿从根长出去，其余的星在同一个前沿上退开，节奏自己慢下来。不要动。P2 认为“绿色从白色乱图里长出来”正是页面的论点。
  • 还有一层：这是你定的。README 约定 2 写着，绿线都是乱图里本来就有的。
  • 我的判断：两边说的是两件事，都成立。含义上证据支持 T1、T2：我的连拍里绿色确实是沿着还亮着的白线走、把白星点绿。作为动作它也确实干净。所以不直接改，先改字（第一节第 2 条的第一步），再把“先退场、再新画”做成单独一版并排比较。那一版里星、线、形状、比例都不变，仍然只有一个从根出发的前沿，P3 看重的东西大部分还在。

2. 阶段文字要不要改成图 2 的说法

  • T2：用项目自己的词（repository、capability graph、scope、rewrite、checks、nano），并把这六步排成一行，当前一步亮着，定格时也知道演到哪了。
  • T1、T3：不要把星空叫 capability graph，不要把绿色子图叫 selected scope。页面上星星的比例是代码量的比例（760 颗留 360 颗，就是留下 47.4% 的行），页面又说 Detectron2 的 106 项能力全部保留。如果星空是“能力图”，暗掉 400 颗星就是在说丢了一半能力。
  • 我的判断：证据支持 T1、T3，星星继续代表代码。T2 建议的另一半可以单独采纳：把几个阶段排成一行小字，当前一步亮着，手机上只显示当前一步。根源是图 2 和页面对“星星代表什么”的说法不同，值得你定一次。

3. 读数：两行两条，还是并成一条

  • P2、P5：并成一条横条（灰的底是原仓库，绿的填充是 nano）加两个数字。两行两条是一块仪表盘，ORIGINAL 那条永远是满的。
  • T1、T2、T3、P4：两行的形式是首屏最如实的东西。同一把尺子、同一套检查、nano 从 0 涨上来，“从零”和“一半”只在这里被真正演出来。要改的是它的话，不是它的形式。
  • 我的判断：电脑上保留两行（这也是约定 5），改字、去掉 “100% tokens” 和开始前的 “0 / 382 pass”（第一节第 5 条）。删掉跑马灯之后，首屏底部已经不挤了。手机上横条只有几十像素，按第二节第 8 条让横条通栏。

4. 三个大数字，留不留在首屏

  • P5：搬到结果一节的开头，首屏只留一种说法。P2：留两个，用时搬走。P1、P4、T3：已经是完成的作品，不动。
  • 我的判断：不动。1440×900 时它们本来就在第一屏之外，首屏结束在读数下面，不和画面抢。删掉跑马灯、读数在交付时改用减号的写法之后，“三层、两种记法”的问题已经没有了。
