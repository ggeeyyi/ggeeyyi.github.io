同一份清单、同一个选中范围，只改一个开关，各跑一次完整作业。下面把两次作业的每个模型会话和每个步骤画在时间轴上，再按部分汇总时间和 token，最后回答按功能并行写代码有没有带来收益。

结论：这一对运行里，看不出并行带来了收益。

并行模式做两件事：把冻结阶段同时进行的会话数从 8 放宽到 16，以及把代码按 scope 分给几个作者同时写。前一件让「写测试事实」快了 11.9 分钟，但冻结的其余步骤没有变快。后一件，并行组本身是通的：三个 scope 同时写，58.1 分钟的工作在 23.3 分钟内完成，合并没有冲突；可是把代码拆成 4 个 scope 之后，每个会话并没有按比例变短，写首版代码的墙钟时间是 43.2 分钟对 44.9 分钟，基本持平，token 多了五成。

全程时间线

横轴是提交作业后的分钟数，两次作业用同一把尺。一个色块是一个模型会话或一个本机步骤，上下叠在一起的色块同时进行。冻结阶段 off 同时最多 8 个会话，on 最多 16 个；写代码阶段 off 始终只有 1 个作者，on 有一段是 3 个。

  • 两次作业的大半时间都在冻结。off 的冻结 152.1 分钟，on 的 205.4 分钟。
  • 写测试事实，on 叠得更高、结束得更早。并行模式把这类会话的并发上限从 8 放宽到 16，这一步从 34.3 分钟降到 22.5 分钟。
  • 设计测试没有因此变快。这一步是一批一批做的，每一批的会话数本来就不多，一批要多久取决于其中最慢的那个会话。on 的第一批用了 38 分钟（off 是 25 分钟），其中一个会话跑了 29 分钟。测基线两边用时也差不多。
  • on 的冻结多出一段。控制器在封存前为一个叶节点又设计了一轮测试，之后还得再测一次基线，一共多花约 50 分钟。off 的控制器在同样的局面下直接封存了。
  • 写代码阶段的形状不同。off 是一条线，on 在中间有一段三层叠放，就是并行组。

放大：从第一次作者调用到交付

把两次作业对齐到各自第一次作者调用开始的时刻。S1–S4 是 scope 的编号；两次作业的划分不同：off 是 2 个 scope 依次写，on 是 1 个地基加 3 个并行部分。

  • 写首版代码，两边用时差不多。off 的两个 scope 依次写完是 +43.2 分钟。on 的地基 20.2 分钟，并行组 24.6 分钟（S2、S4、S3 三个会话分别 23.3、17.0、17.9 分钟，同时进行，合并 1.3 分钟、无冲突），合计 44.9 分钟。
  • off 的首版草稿被整体驳回。保存时发现 45% 的行与原版重复，两个 scope 又各重写了一遍（49 分钟），所以第一个能保存的完整候选到 +97.3 分钟才出现。on 的地基只有 1 个函数超限，6 分钟改完，完整候选在 +52.2 分钟出现。这 45 分钟的差距来自原创性检查，不是并行。
  • 修复阶段 on 更慢。off 只差 1 个检查，一次 5 分钟的修复就过了。on 也只差 1 个检查，但先重写了一批与原版重复的函数（22 分钟），又修了两次文档配置，中间还被驳回一次。
  • 控制器的开销变多了。off 6 轮共 15.0 分钟，on 9 轮共 19.4 分钟。

每一部分花了多少时间和 token

每一行是作业里的一类工作，上面一条是 off，下面一条是 on。墙钟时间是这类工作占用作业的时间；token 是这类工作里所有模型会话的合计。输入 token 里绝大部分是缓存读取：会话每一轮都要重读自己的上下文。

  • token 的大头在冻结。设计测试一项就占了两次作业输入 token 的四成到五成，费用上冻结占八成多。写代码（首版加重写修复）的费用是 $60 和 $68。
  • 并行让写首版更贵。首版的 token 是 21.3M 对 32.4M（+52%）：4 个作者各自要读一遍契约，后 3 个还要读地基的代码。
  • 算上重写和修复，两边接近。作者会话的 token 合计 45.9M → 42.5M（-7%），因为 off 把两个 scope 都重写了一遍，把首版省下的又花了回去。
  • 阶段 01 不在图里。宿主做能力清单的阶段 01 只在 off 做了一次（35 分钟，$34，输入约 67.4M token），on 直接复用它的结果，所以两次作业的清单完全相同。

按功能并行带来收益了吗

分五层回答：冻结里的并发、并行组本身、写首版这一步、写代码到交付、整个作业。

冻结里放宽并发：只有一步变快

写测试事实从 34.3 分钟降到 22.5 分钟（-35%），这是这一对运行里并行模式唯一确定省下的时间。设计测试和测基线没有变快：前者受最慢的会话限制，后者两边用时相同。

并行组本身：有效

三个互不依赖的 scope 同时写，墙钟从 58.1 分钟压到 23.3 分钟（2.5 倍）。合并没有冲突，也没有哪个作者因为看不到别人的代码而返工。机制是通的。

写首版这一步：没有变快，而且更贵

墙钟 43.2 分钟对 44.9 分钟。并行省下的时间，被「拆成更多会话」多出来的工作量抵消了：会话累计 43.1 → 78.3 分钟，token 21.3M → 32.4M，费用 $29 → $48。

写代码到交付：on 快 11 分钟，但原因不在并行

off 的首版被原创性检查整体驳回，重写用了 49 分钟；on 只返工了 1 个函数。之后的修复 off 用 5 分钟，on 用了 31 分钟。这两项都取决于模型这一次写出了什么，和是否并行没有可见的关系。

整个作业：on 慢 43 分钟，原因也不在并行

冻结占作业的 57%–66%。on 的控制器在封存前多设计了一轮测试，冻结多了 53.3 分钟，远大于写测试事实省下的 11.9 分钟。写首版代码在 on 的作业里只占 14%。

由此推出：什么时候并行才会有收益

  • 这次的选中范围太小。5.25 万 token 只比一个 scope 的上限（4.5 万）多一点，串行 2 个会话就能写完。并行要先写地基再写一层，至少也是两个会话的墙钟时间，所以打平。
  • 选中范围是上限的好几倍时才值得。按这次每个首版会话约 20 分钟推算：串行要写 N 个 scope 就是约 N × 20 分钟，并行是地基加一层，约 40 分钟。N 到 4 以上差距才明显。这是推算，不是实测。
  • 代价是 token。并行换来的只能是墙钟时间。会话越多，重复读上下文的开销越大，这次首版的 token 多了一半（+52%）。

要得到可靠的结论还缺什么

  • 重复。每种配置至少再跑两三次，才能把并行的效果和控制器判断、原创性检查带来的波动分开。
  • 把两件事分开比。冻结里的并发放宽和写代码的并行是两个独立的改动。让两次运行共用同一份封存好的契约、只比封存之后的部分，冻结的波动就不会混进来。
  • 更大的选中范围。在串行需要 4 个以上 scope 的项目上再比一次，才是并行模式本来要解决的情形。

名词和口径

scope
一组文件互不重叠的能力，最多 4.5 万原版 token，交给一个作者会话写。并行模式下划成一个地基加几个互不依赖的部分。
冻结
写测试事实、测原版基线、设计测试、封存契约。封存后测试和基线不再改，之后才开始写代码。
原创性检查
保存候选时把新代码和原版逐行比较。重复超过 40%，或单个函数超过 60%，就拒绝保存。
墙钟时间
实际流逝的时间。几个会话同时进行时，墙钟时间小于它们各自时长的总和。
输入 token
会话每一轮发给模型的全部内容，含缓存读取。输出 token 含模型的思考。
  • 数据来自两次作业自己的记录：每个模型会话的起止时间和用量，每个步骤的起止时间。各部分的墙钟时间相加等于作业总时长。
  • 两次作业的清单、选中范围、基准提交、运行器、时限和 nanolize 版本相同。不同的只有并行模式：最多 4 个作者同时写，并且放宽三处并发（冻结里的模型会话 8 → 16，敲除检查 4 → 8，同时运行的检查 1 → 8）。
  • 两次作业有一段重叠：off 写代码的时候，on 正在冻结，两边同时调用模型。off 的写代码阶段可能因此略慢。
  • off 的最后一次修复和 on 的一次文档修复，按规则借给作者看了对应能力的原版文件。
  • 页面里没有写出运行所在的机器、路径和账号。
