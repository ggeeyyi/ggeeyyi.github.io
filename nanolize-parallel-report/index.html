背景：并行模式怎么工作

  • controller 策略一个看不到源码的 controller 每轮选一批工具调用；它选不出来时，由一条默认主线兜底。
  • 并行开关由 owner 打开（parallel=on）。默认 4 个作者同时写，并把冻结、检查等环节的并发度加宽。
  • 并行组run_parallel_agents 接 2–20 个同角色请求，各自在独立工作区里写。split 合并成一个候选，speculate 并排保留多个版本。
  • 并行主线首次实现按依赖层写，一层有多个 scope 就开一个 split。修复时，如果每个失败的问题只属于一个 scope，也开 split。

proposal 之外的并行改进点

以下来自读代码，没有实测。

1

并行组对部分失败不健壮

建议优先

现在会发生什么

  • 组里任何一个会话因限流或额度没跑起来，整个作业暂停，其余已完成会话的草稿既不保存也不合并。
  • 恢复后主线认为这一层什么都没写，会开新工作区把全部请求重跑一遍。
  • 任何一个会话失败（非零退出或超时），主线就放弃分层，剩下的 scope 不再按层写。组越大，撞上的概率越高。
  • nanolize 这一层没有重试或退避，而加宽后同时开的会话更多，更容易撞限流。

建议

  • 暂停前先把已完成的会话保存成候选。
  • 恢复时只补缺的请求。
  • 失败的请求当作一次重写，不终止分层。

证据：job_tools/workspaces.py:684-689 strategies/advice.py:946-952 execution.py:3027

2

雷同限制和并行组叠加会更糟

建议优先

现在会发生什么

  • auto 模式下，工作区草稿超线只会拒绝保存，不会把作业切到“告知作者”的状态。只有作业自己的 run_agent 和 save_candidate 会切。
  • 知名项目上一个 N 路 split 可能全部被拒，结果是 no_candidate。主线退回成一次整体实现，而这次作者仍然没被告知，还会再被拒一次。
  • 现有的并行测试没有覆盖这个组合。

建议

  • 按 proposal 第 6 节把默认改成 on，问题直接消失。
  • 如果保留 auto，工作区触发超线时也要切换作业状态。

证据：job_tools/workspaces.py:464-483 original_overlap.py:151 job_tools/authoring.py:789,1004

3

并发度没有统一管理

建议优先

现在会发生什么

  • 作者、冻结会话、knockout、任务测量、检查各有各的线程池，宽度来自常量或配置时的 CPU 配额。
  • 完全不看限流、进程和线程上限、内存，也没有跨作业的限制。
  • 加宽后是 16 个冻结会话、8 个检查 worker、4 个作者。在有进程或线程上限的共享机器上直接跑，可能打满。

建议

  • 加一个作业级的会话总数上限，所有池共用。
  • 宽度在 worker 实际运行的机器上算，并参考进程上限和内存。

证据：execution.py:1205-1222 check_executor.py:295-311

4

重写是串行的

值得做

现在会发生什么

  • split 里没保存成功的请求和丢了路径的请求，都由主线逐个 run_agent 重写，每个占一次尝试。
  • 没保存成功的请求彼此独立，本可以再开一个 split。只有真正冲突的才需要串行。
  • 主线重写时用的是原请求，不会告诉作者丢了哪些路径。

建议

  • 没保存成功的请求合成第二个 split。
  • 冲突的一方单独重写，并在指令里写明丢失的路径。

证据：strategies/advice.py:1112-1117

5

合并只按路径，先到先得

值得做

现在会发生什么

  • 所有工作区都从同一个 base 出发，本可以做文本级三方合并。现在是整文件判冲突，输的一方整体重写。
  • 为了避免冲突，作者被禁止碰共享文件（如 __init__.py），合并后这些文件常常缺内容。

建议

  • 对冲突的文本文件先尝试三方合并，失败再走重写。
  • 这和 proposal 5.1 的集成步骤互补。

证据：job_tools/authoring.py:1275-1318，提示词 author.scope.concurrent

6

作业同一时刻只能有一个操作

值得做，改动较大

现在会发生什么

  • 写代码和验证不能同时进行，所以分层实现要全部写完才第一次验证，地基的错误会带进后面各层。
  • speculate 的多个版本只能逐个恢复、逐个比较，主线不会替 controller 挑。

建议

  • 允许在独立工作树里并行验证候选。
  • speculate 组自动比较并排序。

证据：job_tools/background.py:1-20，提示词 controller.parallel

7–9

较小的三项

小项
  • 主线修复只要有一个问题跨 scope 或不属于任何 scope，整轮就退回串行（strategies/advice.py:1150-1177）。可以先并行修单 scope 的问题，再单独处理跨 scope 的。
  • 层与层之间整层等齐，慢的 scope 会拖住下一层里不依赖它的 scope（strategies/advice.py:1120-1147）。
  • 实现工作区在作业期间从不清理，每个并行组留下 N 份副本。

建议的优先顺序

  1. proposal 第 6 节：雷同限制默认改成 on。同时解决新改进点 2。
  2. proposal 3a：拦住只为体积的优化。
  3. proposal 3b：并行组按请求计数。
  4. 新改进点 1：部分失败时回收已完成的会话。
  5. 新改进点 3：统一的并发上限。

前三项改动小。后两项决定并行模式在限流和资源受限的环境下能不能稳定跑。

核对方式和没核对的部分

  • 全程只读。proposal 基线 2d4682f 是 main 的祖先，其后有 202 个提交，73 个源码文件有改动。

  • 没有运行带 controller 的作业，所以 proposal 里的用时和花费数字没有复核。
  • 新改进点来自读代码，没有实测。
  • 同一提交上 README 的五个离线 demo 全部通过，退出码都是 0。
