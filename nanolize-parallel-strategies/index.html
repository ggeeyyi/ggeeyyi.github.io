nanolize main 的并行策略

main 里的并行分三层：两个作业之间、一个阶段内部、以及 controller 在修复阶段自己选用的分组。下面用同一个示例项目，把它们和一条全串行的基线画在一起。

第一层

作业之间：pair

main job 做 freeze（写测试、封存），draft job 同时写首版代码。是否拆成两个作业在提交时按规则决定。

第二层

阶段内部：主线按规则展开

写测试时每个 leaf 一个 session；knockout 多个 leaf 同时做；写首版代码时同一层的 scope 同时写。

第三层

controller 自选

第一次全量比较之后，controller 可以把修复拆给多个 author、让几个版本并排，或在独立 workspace 里各写各的。

名词

leaf
capability 树上的叶子。测试按 leaf 设计。
scope
一组文件互不重叠的 capability，最多 45,000 原版 token。代码按 scope 分给 author，scope 之间有依赖时分层。
freeze
抓原版 baseline、设计测试、封存合同。封存后测试不再改。
knockout
在原版副本里禁用一个 leaf 的代码再跑 check，确认测试真的在测它。
全量比较
候选代码在所有 check 上对比原版 baseline。第一次全量比较返回之后，controller 才开始参与决策。

同一个项目，四种跑法

示例项目：6 个 leaf 需要测试，5 个 scope 分三层（1 / 3 / 1），第一次比较后有 3 个 scope 出问题。一格代表一份工作，上下叠在一起的格子同时进行。

  • A → B 不需要任何开关。freeze 从 15 格变成 6 格：6 个 leaf 的测试同时写，knockout 4 个一批。首版从 5 格变成 3 格：第 2 层的 3 个 scope 同时写。
  • B → C 是 pair。首版实现挪到 draft job，和 main job 的 freeze 同时进行；main job 封存之后才导入草稿，所以草稿影响不到测试。
  • C → D 是 parallel 模式。修复按 scope 拆成一组同时修；knockout 的并发从 4 放宽到 8，6 个 leaf 一批做完。
  • A 只是对照，不是 main 的某个配置。main 里最接近它的是 fixed 策略：代码一个 scope 接一个写，但写测试和 knockout 仍然并行。

并行清单

每一行是一处并行。「默认」表示不需要任何开关；「parallel 模式」由 owner 在提交时打开，controller 不能自己开关，也不能改并发上限。

split 和 speculate 的区别

两者都是 parallel 模式下的 author 分组，都从同一个候选出发，区别在结果怎么收。

仍然串行的地方

  • 层与层之间。后一层的 scope 要基于前一层写好的代码。一个超过 45,000 token 的大组会被切成几段，段与段之间也是串行。
  • 单作业里的 freeze 和 rewrite。没有 pair 时，必须封存之后才能开始写代码。
  • 默认的修复。不开 parallel 模式时，一轮修复是一次 author 调用。
  • controller 的一批调用。一批最多 24 个调用，逐个执行。一个作业同一时刻只有一个改状态的操作在跑；后台调用运行时，只有查询和取消可以同时应答。
  • author 调用次数不够时。owner 给的次数不够分层用，整个选择范围退回一次调用。
  • 小项目。只划得出一个 scope 时没有可并行的代码工作；选择范围不到 20,000 token 时默认也不拆成两个作业。
