nanolize 分层版本实施方案：v0 → v1 → v2

新版本要做成 host agent → controller → author / test designer / verifier 三层，一版一版把流程交给 controller。三个版本跑的是同一条流程，功能保持一致，区别只在哪些步骤先问 controller：v0 由它排 author；v1 再加封存之后的每一步（保存、第一次全量对比、导入），以及封存之前给 leaf 加 designer 会话；v2 再加封存之前要不要补一次设计。baseline 的抓取和封存，三个版本都由 mainline 执行。

两个开关

pair

管 draft job 和 main job 是否重叠。三个版本都不改它的含义。

  • 关：一个作业。首版排在封存后面。
  • 开：两个作业同时跑。main job 冻结合同并验收；draft job 在仓库的第二个克隆上同时写首版。
  • 不写：程序自己定。选中的代码不少于 20,000 token，并且有计算节点可用，就是两个。
parallel

管其余所有和并行有关的事。这是 v0 起的含义，三个版本相同。默认是关。

  • 关：author、repair、test designer、reviewer 的会话一个接一个。排队等待不算超时。这时 owner 没有并发数可给：这个选项移除，给了入口会拒绝。
  • 开：下面这些并行流程才可用：多个 author 同时写；同时给多个 leaf 写测试；同时修几处；draft job 提前验证，用已经固定的那部分测试先对比、先修。author 和修复的并行由 controller 在 owner 的上限内安排。
  • 现在不是这样：谁来规划也挂在这个开关上；关着时仍有并行（test designer 全部同时开，同一层最多 4 个 author）。

两个开关都由 owner 在入口命令里给，或由 host 代填。controller 看得到它们，改不了。

三个版本：自由度一级一级放开

三个版本跑的是同一条流程，区别只在哪些步骤先问 controller。每一版都建在上一版上面，做完就是一个能单独使用的版本。三级台阶不一样大：v0 是一大步，但只在 parallel 关着时；v1 是中等的一步，主要在封存之后；v2 是一个二选一。原因见评审之后改了什么。

v0

controller 排 author。封存后由它排首版，parallel 开或关、两个作业都是。parallel 关着时所有会话一个接一个，程序不划分 scope。

test designer 仍由程序排，controller 在封存之前不被问。保存和第一次全量对比之前不单独问它；导入时一律等。parallel 开着时，谁来定和今天相同。

v1

封存之后每一步都先问 controller；封存之前它可以给 leaf 加 designer 会话。在 v0 上加：到保存、第一次全量对比这几步先问它一轮，它能看了上一步的结果再定；parallel 开着时，导入等不等 draft job 由 main job 的 controller 定；设计之前问它一轮，它可以给点名的 leaf 另加会话。

baseline、封存、每个 leaf 默认的 designer 会话仍是 mainline 的。

v2

封存之前要不要再补一次设计，由 controller 定。在 v1 上加：第一次设计之后问它一轮，照常封存，还是先给还缺有效测试的 leaf 补一次设计。

baseline 的抓取和封存本身仍由 mainline 执行，这是你定的。第一次设计覆盖全部目标、门、试跑、评审和封存的检查仍归程序。

三个版本都不变的

你要求现有流程的功能在 v0 到 v2 里尽量保持一致，只是自由度变多。我按下面五条来守。

  • 步骤和工具不变。三个版本跑的都是今天这串步骤：准备、baseline、设计测试、封存、首版、对比、修复、交付。没有删掉的阶段，也没有换掉的工具；新增的只有工具上的几个参数。
  • 默认就是上一版的做法。每个新放开的决定点上，mainline 会走的那一步作为默认给 controller 看。它没有可用的回答、预算用完、或者放行 mainline，走的就是上一版的步骤。例外只有一处，是你定的：parallel 关着时，v0 的默认做法本身和今天不同。
  • 证据规则归程序。给哪些 leaf 至少设计一次、门、试跑、knockout、评审裁决、封存的检查、对比怎么判、交付上限，三个版本都不交给 controller。baseline 的抓取和封存也都由 mainline 执行。
  • 封存之前只许加，不许减。controller 在封存之前能做的只有两件：v1 起给 leaf 另加 designer 会话，v2 起补一次设计。每个 leaf 默认的会话、第一次设计覆盖全部目标，它都改不了。测试写什么仍是 test designer 的事，算不算有效仍由程序判。
  • 两个开关的含义相同。pair 管两个作业是否重叠，parallel 管其余所有并行。parallel 关着时和今天不同的地方都来自同一条规则，是你定的：所有会话一个接一个。具体是三处：首版不划分 scope；designer 和 reviewer 一次一个；workspace 那组工具一次一个。

v1：封存之后每一步都先问 controller；封存之前它可以给 leaf 加 designer 会话

和 v0 比，变了什么

  • 到保存和第一次全量对比这几步先问 controller。封存之后每一步都先问它，它能看了上一步的结果再定：写完一批先比一部分 check，再决定下一批怎么写。它没有可用的回答时 mainline 照旧做。不问的步骤有四个：导入（下一条的情况除外）、任务基准的准备、候选环境的重新准备、draft job 的交出。

实测上的结论

  • 在 tqdm full 上，三个版本新增的自由度大多用不上：项目小，controller 多半选一次写完；设计一次之后缺有效测试的 leaf 是 0；draft job 比封存早交出。
  • 所以 tqdm full 验证的是没有退步和多问几轮的开销。新路径靠脚本化 controller 的测试覆盖。
  • 要看到新自由度被用上，需要另一个项目，等 tqdm 的结果出来再定。

现在

为什么只做加法

原方案让 controller 排三样：会话的先后、把一个 leaf 分成几个会话、同时几个。评审逐条对了代码：

  • 先后是名义上的。同一轮里各 leaf 的会话互不相见，试跑和评审对整轮只做一次。所有会话都跑完时，先后不影响结果；时间不够时，它决定的是谁没有测试。
  • 同时几个只能往坏里调。默认已经是全部同时开，调低只会不变或更差。
  • 把一个 leaf 拆开会让测试变少。下一轮问不问是按 leaf 判断的：拆成 4 个会话只要 1 个成功，另外 3 份功能点就没人补。

所以 v1 只留“另加会话”这一样，并且让默认会话完全不受影响。这一轮手里只有计数，是整个流程里信息最少的时候；按结果判断哪里要补，要等 v2 的“补一次设计”。几个小 leaf 合用一个会话也不做：设计引擎是按“一个会话一个 leaf”写的，合并要重写大半个主循环。

v2 的改动：封存之前要不要再补一次设计，由 controller 定

v2 只加一个决定：第一次设计之后、封存之前，要不要再补一次设计。你定的：baseline 的抓取和封存本身仍由 mainline 执行。封存之后和 v1 完全相同。顺序是先立规则和工具表（W13），再做上下文（W14），最后才接通那一轮（W12）：今天的工具本身不拦少设计、反复设计和强制重抓，规则要先立起来。

  • 收益。今天还缺有效测试的 leaf 会一直缺到交付：对应的 capability 没有检查能证明它保持了行为，交付状态最多是“有缺口的完成”。补一次让这些 leaf 有机会补上。
