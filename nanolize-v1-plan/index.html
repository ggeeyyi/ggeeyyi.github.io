nanolize v1 实施方案

新版本要做成 host agent → controller → author / test designer / verifier 三层，并逐版把自由度交给 controller。v1 是第一步：所有 author 和 test designer 的拆分与并行都由 controller 决定，运行仍然是 main job 加 draft job 两个并行的作业。这页先写清我对 v1 的理解，再给出要改什么、按什么顺序改、怎么验证，以及需要你定的几件事。

我对 v1 的理解

v1 改两条线
  • controller → author：现在只有 owner 打开 parallel 才归 controller。v1 里它是每个 controller 作业的常态，两个作业都是；并去掉几处仍然写死的规则（共享文件谁写、只能按程序切好的 scope 分）。
  • controller → test designer：现在完全没有这条线。v1 新建：封存之前给 controller 一轮，由它决定 test designer 的拆分和并行。
v1 不改的
  • 两个作业的结构：main job 冻结合同并验收，draft job 同时写首版。拆不拆仍由程序规则和 pair= 决定。
  • verifier 这条线：冻结里的 baseline、封存、第一次全量对比仍归 mainline。
  • 证据规则：给哪些 leaf 设计测试、门、试跑、knockout、评审裁决、对比怎么判，全部照旧。
  • owner 的上限：同时几个 author、同时几个 designer 的上限仍是 owner 的。
mainline 在 v1 里还剩什么
  • 执行没有取舍的步骤：建工作区、抓 baseline、封存、导入草稿、第一次对比。
  • 兜底：controller 没给出可用回答时，照今天的固定做法走。
  • 补漏：controller 的安排漏掉的 leaf 或 capability，由它补上，保证一个不少。

一句话：v1 之后，“开几个会话、怎么分、同时几个”这类决定，在 author 和 test designer 两处都归 controller；程序只保留证据规则、上限和安全网。

W1　规模：小

W2　规模：小

规划轮的失败不连累修复

现在
controller 连续 3 轮给不出可用回答，这次启动剩下的部分就全走 mainline。规划轮和修复轮共用这个计数，所以首版规划答不好，后面的修复也没人管了。
v1 怎么改
规划轮（首版、设计测试）失败后直接走 mainline 的默认做法，不计入这个次数，或在默认做法成功后清零。
改哪里
controller.admission 里数失败次数的那一段。
测试
test_job_tools 的 admission 用例，test_parallel_paths.RepairPathTests。
W3　规模：中

共享文件由 controller 指定负责人

现在
并行组里每个按 scope 写的 author 都会自动收到一句“别人也在写，不许建或改共享的包级文件”。detectron2 那次 controller 只能在自己的指示里反着说，给每个 __init__.py 指定负责的 scope；author 同时拿到两句互相矛盾的话，没有文字说哪句优先。
v1 怎么改
请求里加一个字段，说明这个请求是否负责共享文件。程序按它生成给 author 的那句话：负责人被告知“你的指示里点名的共享文件归你写”，其他人仍被告知不要碰。修复组默认不再附这句话。
改哪里
请求的 schema（authoring.REQUEST、workspaces.GROUP_REQUEST）、authoring.request_feedback、scopes.brief、提示词 author.scope.concurrent。
测试
test_parallel_agents、test_parallel_scopes 里关于这句话的两个用例；提示词快照。
W4　规模：大

按 capability 自由分组也能记账

现在
程序只按 scope 记“写了什么”。controller 的请求一旦按 capability 写，记账就停了：mainline 不再补写漏掉的部分，controller 看到的“还剩什么”也不准，只能等对比暴露问题。draft job 交出草稿时还会把所有 scope 都记成“已写”。另外 controller 看不到每个 capability 多大、哪些 capability 共用文件，没法自己分。
v1 怎么改
记账单位改成 capability（被切成几段的大组仍按段记）。任何分法之后 mainline 都知道还缺什么并能补写。把一个共用文件的组拆到两个请求里会被拒绝，并说明原因。给 controller 多看三样东西：每个 capability 的原版 token 数、共用文件的分组编号（不给路径）、不拥有文件的 capability。按 capability 的请求也给它那一份大小目标。
改哪里
advice._implements、_authored、_layer；controller._plan；finish_draft 记录的内容和 draft job 的完整性检查；authoring.scopes_context；scopes.size_share 和 brief；run 页面读“层”的两处。
测试
test_parallel_mainline 的 HelperTests、LayerTests、PartTests；test_scopes；test_pair_jobs 里关于交出内容的用例；run 页面的测试。

v1 不改的 author 规则

  • 一个组 2 到 20 个请求、同一种角色、整组算一次 author 尝试；这些是计费和合并的机械规则。
  • 合并时靠前的请求保留同一路径；丢了文件的请求由 mainline 重写，除非 controller 自己接手。
  • 程序的 scope 切法（45,000 token 上限、共用文件的 capability 不拆开）保留，作为默认建议和兜底。要不要让 controller 改这个上限，见“v1 不做的”。

test designer 这条线的改动

这条线是新建的，也是 v1 里最需要小心的一处：现在的代码特意不让 controller 在封存前参与，为的是它影响不了测试。v1 的做法是让它只决定结构（怎么分、同时几个），内容和验收一概不碰。

W5　规模：中

设计引擎接受“同时几个”和“一个 leaf 分几个会话”

现在
design_tests 不接受这两个数：同时几个从 owner 的策略里读（没给就全部同时），一个 leaf 只在要迁移的原版测试超过 40 个时才有多个会话。
v1 怎么改
加两个参数。同时几个只作用于 designer 的线程池，reviewer 的池子不变；有上限（owner 的数或 32）和下限（保证每个会话在窗口内来得及开始）。分几个会话复用迁移批次的机制：给这个 leaf 多排几个会话，程序按固定规则把它的功能点和知识条目分给各会话，每个会话有自己的文件名前缀，被拒的反馈回到写它的那个会话。新增一段提示词告诉 designer 它只负责 leaf 的一部分。
改哪里
leaf_test_design.design_tests：线程池大小、batches 和会话单元、payload、told（反馈路由）；新提示词 test_designer.part。
测试
照 test_migration_design 的写法（脚本化的 runner）新增用例：分 2 个会话、反馈路由、文件名前缀、同时几个的上下限；test_leaf_test_design 里数线程池大小的用例。
W6　规模：中

design_leaf_tests 工具接受 split

现在
工具只有一个参数 leaves（只设计点名的 leaf）。分几次调用可以做到分批，但调用之间是串行的，每次调用各付一遍试跑、评审和时间窗口。
v1 怎么改
加参数 split：{groups: [{leaves: [...]} 或 {leaf, parts}], max_parallel}。一次调用内生效，共用一个窗口、一次试跑、一组评审。程序先算好目标名单，再把 split 套上去：名单外的 id 忽略并报告，名单里没点到的照默认。结果里写明实际用的拆分。
改哪里
job_tools/freeze.py 的工具注册和 _designed；execution._freeze_designed_tests（把 split 规范化后传下去，并写进设计记录）。
测试
照 test_flexible_freeze 和 test_design_calls_job 的写法：带 split 的调用设计了全部目标；名单外的 id 被报告；不带 split 的调用和今天逐字节相同。
W7　规模：中

封存之前给 controller 一轮

现在
controller.admission 规定第一次全量对比之前不问 controller，代码注释写明理由：封存前不被问的 agent 没法通过选择影响测试。封存前那一轮的机制其实还在（上下文里有 design_left，阶段叫 freeze），只是被这条规则挡住了。
v1 怎么改
当 mainline 的下一步是 design_leaf_tests 时问 controller 一轮。这一轮：工具表里只有 design_leaf_tests；上下文新增 test_design 一段，列出每个目标 leaf 的计数、owner 的并发上限、时间窗口；预算只算本作业自己的。回答不可用就走 mainline 的默认调用（今天的行为）。新增一段 controller 提示词讲这一轮。
改哪里
controller.admission、visible_tools 和回答的 schema（封存前收窄）、controller._context、freeze.design_left（加每个 leaf 的计数，取消 50 个的截断或改成分页）、提示词 controller.guide 开头和新段落。
测试
照 test_first_implementation_plan 的写法：封存前只在这一步问一轮；别的工具调用被判无效；不回答时走默认；pair 的 main job 里 draft 的 token 用量不影响这一轮。原来断言“封存前从不问”的三个用例要改。

这一轮里 controller 碰不到的东西

v1 之后“agent 影响不了测试”这条保证具体靠下面几条守住。controller 能做的事只会让测试更多或更早，不会更少或更松。

它想做的事能否靠什么守住
给哪些 leaf 设计测试不能名单由程序按 baseline 算。split 里没点名的 leaf 照默认开一个会话；点了名单之外的 leaf 会被忽略并报告
少开会话不能每个 leaf 至少一个会话，和现在一样。controller 只能加（一个 leaf 最多 4 个）或调顺序
给 designer 写文字不能split 只有结构：leaf 的顺序、每个 leaf 分几个会话、同时几个。提示词仍由程序拼
看源码或测试不能这一轮给它的只有每个 leaf 的计数：功能点数、知识条目数、源码 token、要迁移的测试数、缺测试的原因代码
调别的工具不能封存之前这一轮的工具表里只有 design_leaf_tests。封存、抓 baseline 仍由 mainline 调
改门、试跑、knockout、评审不能这些代码不动；一个测试算不算有效和谁排的会话无关
让设计来不及做完不能同时几个有下限：程序按时间窗口算出最少要同时开几个，低于它就抬上去并在结果里说明
看到 draft job 的情况不能这一轮的上下文和预算只算 main job 自己的；draft job 花了多少 token 不影响这一轮问不问

为什么不做“几个小 leaf 合用一个会话”

读代码的结论是不划算：designer 的提示词、payload、目录、文件归属、反馈、失败记录全是按“一个会话一个 leaf”写的，合并要重写设计引擎的大半个主循环；而会话本来就能全部同时开，合并只省模型调用，不省时间。v1 里 {leaves: [...]} 的含义是“这几个 leaf 各自的会话排在一起、按这个顺序开”。

工作包和顺序

每个工作包是一组独立的提交，带自己的测试，做完一个就能跑全量测试确认没有新增失败。顺序的想法是：先把已经通了一半的 author 线变成常态（W1–W3），再接通 test designer 线（W5–W7），配套文字和页面跟上后实测一次；最大的一块 W4 放在后面，作为 v1 的第二步。

W3共享文件由 controller 指定负责人中W1并行写首版时不再有互相矛盾的两句话

W6design_leaf_tests 的 split 参数中W5owner 手工调用就能用 split，还不涉及 controller
W7封存前的规划轮中W6controller → test designer 这条线接通

规模是相对的：小 = 几处判断加改测试；中 = 一个模块里的新逻辑加一组新测试；大 = 跨五六个模块，要动几十个现有用例。

怎么验证

单元测试
  • 每个工作包新增回归测试，写法照搬现有的三种：脚本化的假 runner、打补丁的 design_tests、脚本化的假 controller。
  • 全量测试在计算节点上跑，和 main 的失败清单逐条比对，要求没有新增失败。
  • 改了 agent 会读到的文字后重新生成提示词文档和快照。
要专门盯住的不变量
  • 不带 split 的 design_leaf_tests 和今天逐字节相同。
  • 带任何 split，拿到 designer 的 leaf 集合都等于程序算出的目标集合。
  • 封存前那一轮里，除 design_leaf_tests 外的调用一律无效。
  • controller 不回答时，两条线的行为都和今天的 mainline 一样。
实测
  • v1a 做完后：detectron2 核心，和上次相同的配置跑一次。上次是 127.6 分钟、$156.5（另加 host $37.8）。
  • 看三样：两个作业各自的时间线；controller 在设计规划轮里给了什么 split；designer 那一段的墙钟时间和会话数。
  • 实测要占用计算节点和约 $200 的模型费用，开跑前我会先问你。

对效果的预期，先说在前面

  • author 这边：你现在的跑法已经开着 parallel，W1 对它没有行为变化，变的是默认值。实际收益来自 W3（少一类合并后的返工）和 W4（controller 可以按实际依赖分组）。
  • test designer 这边：时间上的收益不会大。detectron2 那次设计测试用了 27.5 分钟，其中 designer 会话只占 10.4 分钟，而且 9 个会话本来就是同时开的；其余是试跑、评审和提交。把最大的 leaf 分成两个会话最多省几分钟，同时会多出一些测试文件要试跑。这条线的价值主要在分层本身，以及 owner 给了并发上限时由 controller 来排先后。
  • 代价：main job 的冻结多一轮 controller，约 1 到 3 分钟、1 到 2 美元。

风险和对策

风险对策
封存前让 agent 参与，削弱“影响不了测试”的保证split 只有结构没有文字；目标名单、门、试跑、评审都不经过它；工具表收窄到一个工具。上面那张表逐条列了守法，每条都配测试
draft job 的花费影响 main job 的设计现在 main job 的 token 计数包含 draft job 的用量。封存前那一轮的准入和上下文改成只算本作业，并加测试

1

parallel 开关在 v1 里是什么意思

现在它既管“谁规划”又管上限和机器并发。v1 里规划权要归 controller，开关得重新定义。

  1. 只管上限和机器并发放宽；规划永远归 controller。想要旧行为用 strategy=fixed。 推荐
  2. 保留为总开关，只把默认值改成开。改动最小（一行），但 parallel=off 会回到 mainline 规划，等于长期维护两套路径；默认还会连带打开机器并发放宽。
2

controller 能不能给 test designer 写文字指示

author 那边 controller 可以写指示。designer 这边如果也放开，它就能影响测试写成什么样。

  1. 不能，v1 只给结构（顺序、分几个会话、同时几个）。 推荐
  2. 能，但限定在“侧重哪些功能点”一类，由程序校验。这会动到保证，建议留到后面的版本单独讨论。
3

test designer 的“拆分”做到哪一步

三种拆法的代价差别很大。

  1. 顺序和分批、同时几个、一个 leaf 分 1 到 4 个会话。 推荐
  2. 再加上几个小 leaf 合用一个会话。要重写设计引擎的主循环，只省模型调用不省时间。

按 capability 自由分组（W4）放在哪

  3. v1 不做 W4，留给下一个版本。

fix-parallel-main 上 3 个没进 main 的提交要不要先并进来

reviewer 的分批要不要也交给 controller

你说的是 author 和 test designer。reviewer 现在每 8 个文件一个，由程序分。

  2. 也交给 controller（每批几个文件，上限 8）。
