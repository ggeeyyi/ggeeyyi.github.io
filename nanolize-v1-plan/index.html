nanolize v1 实施方案

新版本要做成 host agent → controller → author / test designer / verifier 三层，并逐版把自由度交给 controller。v1 是第一步：所有 author 和 test designer 的拆分与并行都由 controller 决定，运行仍然是 main job 加 draft job 两个并行的作业。这页先写清我对 v1 的理解，再画出现在四种开关组合各自的流程，然后给出要改什么、按什么顺序改、怎么验证，以及需要你定的几件事。

我对 v1 的理解

v1 改两条线
  • controller → author：现在只有 owner 打开 parallel 才归 controller。v1 里它是每个 controller 作业的常态，两个作业都是。parallel 只决定 author 并行还是串行：开着时 controller 可以开并行组；关着时一个接一个写，程序不再划分 scope。并去掉并行时仍然写死的规则（共享文件谁写、只能按程序切好的 scope 分）。
  • controller → test designer：现在完全没有这条线。v1 新建：封存之前给 controller 一轮，由它决定 test designer 的拆分和并行。
v1 不改的
  • 两个作业的结构：main job 冻结合同并验收，draft job 同时写首版。拆不拆仍由程序规则和 pair= 决定。
  • verifier 这条线：冻结里的 baseline、封存、第一次全量对比仍归 mainline。
  • 证据规则：给哪些 leaf 设计测试、门、试跑、knockout、评审裁决、对比怎么判，全部照旧。
  • owner 的上限：同时几个 author、同时几个 designer 的上限仍是 owner 的。
mainline 在 v1 里还剩什么
  • 执行没有取舍的步骤：建工作区、抓 baseline、封存、导入草稿、第一次对比。
  • 兜底：controller 没给出可用回答时，照今天的固定做法走。
  • 补漏：controller 的安排漏掉的 leaf 或 capability，由它补上，保证一个不少。

一句话：v1 之后，“开几个会话、怎么分、同时几个”这类决定，在 author 和 test designer 两处都归 controller；程序只保留证据规则、上限和安全网。

现在的四种开关组合：pair 开或关 × parallel 开或关

新分支上还没有改代码，所以这一节画的就是它现在的行为。图是示意图：同一个假想项目，3 个 leaf 要设计测试，首版分成 5 个 scope、两层。画法和流程全图一样：每个作业第一行是控制层发出的工具调用，下面几行是这些调用让谁干活；一列是一步，上下对齐的块同时进行；灰色是 mainline 定的，紫色是 controller 定的。把鼠标放在块上看说明。

开关一：pair

管一次运行是一个作业还是两个。

  • pair=off：一个作业。
  • pair=on：两个作业。main job 冻结合同并验收；draft job 在仓库的第二个克隆上同时写首版。没有可用的计算节点时会被拒绝。
  • 不写：程序自己定。选中的代码不少于 20,000 token，并且有计算节点可用，就是两个；否则一个。
开关二：parallel

默认关。打开后一个开关同时管五件事：

  • 封存后首版怎么切，由 controller 定（否则 mainline 按层写）。
  • draft job 有自己的 controller（否则没有）。
  • 并行修复组、并排试两个版本可以用（否则被拒绝）。
  • owner 的上限生效：同时几个 author（默认 4）、并排试几个版本（默认 2）。
  • 机器并发放宽：knockout 同时 8 个，check 同时最多 8 个。

两个开关都由 owner 在入口命令里给，或由 host 代填。controller 看得到它们，改不了。

它想做的事能否靠什么守住
给哪些 leaf 设计测试不能名单由程序按 baseline 算。split 里没点名的 leaf 照默认开一个会话；点了名单之外的 leaf 会被忽略并报告

调别的工具不能封存之前这一轮的工具表里只有 design_leaf_tests。封存、抓 baseline 仍由 mainline 调

让设计来不及做完不能同时几个有下限：程序按时间窗口算出最少要同时开几个，低于它就抬上去并在结果里说明
看到 draft job 的情况不能这一轮的上下文和预算只算 main job 自己的；draft job 花了多少 token 不影响这一轮问不问

为什么不做“几个小 leaf 合用一个会话”

读代码的结论是不划算：designer 的提示词、payload、目录、文件归属、反馈、失败记录全是按“一个会话一个 leaf”写的，合并要重写设计引擎的大半个主循环；而会话本来就能全部同时开，合并只省模型调用，不省时间。v1 里 {leaves: [...]} 的含义是“这几个 leaf 各自的会话排在一起、按这个顺序开”。

parallel 关着时，test designer 要不要也一个接一个（11-20 新增）

你这次说的是 author。test designer 今天不看 parallel 开关：每个缺测试的 leaf 一个会话，全部同时开。

  1. 不受 parallel 影响。开或关，都由 controller 在 owner 的上限内定同时几个。detectron2 那次 9 个 designer 会话同时开用了 10.4 分钟，一个接一个要 74 分钟。 推荐
  2. 关着时 test designer 也一次一个，和 author 一致。冻结会明显变长。

v1 不做的，留给后面的版本

  • verifier 这条线：冻结里的 baseline 何时抓、封存、第一次全量对比，仍归 mainline。把它们交给 controller 是把“controller → verifier”补全。
  • 两个作业合成一个：现在 main job 和 draft job 各有一个 controller，互不通气，所以“designer 和 author 同时开多少”没人统筹。合成一个作业、一个 controller，才能做跨两边的并行分配。这也要求一个作业能同时跑两个工具，现在不行。
  • scope 的切法本身：45,000 token 的上限、一个大组按文件切成几段。交给 controller 需要让它知道文件一级的信息，和“controller 看不到源码路径”有冲突。
  • controller 影响测试内容：给 designer 写指示、决定给哪些 leaf 设计、要不要再设计一轮。
  • reviewer 和任务评估里的会话：v1 只管 author 和 test designer。

依据。方案基于对新分支代码（21d8a28e，PR #45 的合并点）的阅读：author 的拆分规则在 scopes.py、strategies/advice.py、job_tools/workspaces.py；test designer 的会话在 leaf_test_design.py、execution.py、job_tools/freeze.py；controller 何时被问在 strategies/controller.py。还没有写任何代码，文中的“改哪里”是读代码后的判断，动手时可能要调整。
